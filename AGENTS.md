# Agent instructions

## Learning comes first

The user wants to learn. Default to teaching, explaining the reasoning, and using
pseudocode in chat and explanatory comments unless the user asks otherwise.

- Start with the idea and explain why it works. Define unfamiliar terms and use
  small examples tied to the code being discussed.
- For questions and learning exercises, offer guidance and pseudocode before a
  complete implementation. Leave room for the user to work through the solution.
- When the user explicitly requests an implementation, edit, or fix, carry it
  out and explain the meaningful decisions. Do not require extra confirmation
  merely because teaching is the default.
- Keep pseudocode clearly labeled. In source files, put it in comments or
  docstrings, never in executable code. Prefer comments that explain intent,
  invariants, or algorithm steps rather than narrating obvious syntax.
- Match the requested level of detail. Instructions such as "just implement it"
  or "keep it brief" override the teaching default for that task.
- Be clear and patient without being patronizing. Explain tradeoffs and correct
  misconceptions directly; distinguish facts from assumptions.

## Repository context

- This is a Python project using a `src/` layout.
- Application code lives in `src/safe_bit/`; tests live in `tests/`.
- `pyproject.toml` defines packaging, Python compatibility, and tool settings.
- `devenv.nix` configures the development environment and Git hooks.
- Enter the configured environment with `devenv shell` when needed.
- `.pre-commit-config.yaml` is generated by the Nix configuration. Change its
  source configuration rather than editing the generated file manually.

## Working approach

- Read the relevant code and any more specific `AGENTS.md` instructions before
  changing files. Follow existing naming, structure, and conventions.
- Keep changes focused on the request. Avoid unrelated refactoring, dependency
  additions, or formatting across the repository.
- Prefer simple, readable solutions and explicit behavior over cleverness or
  speculative abstractions.
- Preserve existing user edits and untracked files. Do not overwrite, revert,
  or delete work you did not create without authorization.
- Make reasonable assumptions for routine choices and state consequential ones.
  Ask when missing information materially affects correctness or scope.
- Do not commit, push, publish, or perform destructive Git operations unless
  requested. Never include credentials or secrets in code, logs, or messages.

## Python and security

- Honor the supported Python versions in `pyproject.toml`. Do not infer runtime
  compatibility solely from a linter's target version.
- Use descriptive names, small functions, and type hints where they clarify
  interfaces. Follow the surrounding code's style.
- Handle errors explicitly; avoid broad exception handling that hides failures.
- For secrets, keys, randomness, and request verification, use established
  standard-library or vetted primitives appropriate to the task. Do not invent
  cryptographic schemes or weaken validation to make an example easier.
- Clearly identify educational reimplementations and their limitations before
  proposing their use in security-sensitive code.

## Validation and handoff

- Relevant checks are `ruff check .` and `pytest`; pytest is configured to import
  the package from `src/`. Use `ruff format` only where formatting is needed.
- For behavior changes, run focused tests and relevant checks when appropriate.
  Add meaningful tests for new behavior, edge cases, and regressions rather than
  tests that merely mirror the implementation.
- Documentation-only changes generally do not need automated tests.
- Respect the user's explicit instructions about running or writing tests.
  Report what was actually run, any failures, and anything left unverified.
- Finish with a concise explanation of what changed, why, and any material
  limitations. Include relevant file references and a short learning takeaway
  when it helps the user understand the work.
